# Owner upload signing and Play App Signing

No owner key is committed or generated by this change. Key creation, custody,
Play enrollment and uploads are owner actions; do not reuse the Android debug
key for Google Play. The [official signing guide](https://developer.android.com/studio/publish/app-signing)
(accessed 2026-10-28) distinguishes the upload key from the app-signing key that
Google uses to sign APKs delivered to users.

## Build configuration

Release uses an owner upload key when all four fields are supplied. Environment
variables override the corresponding property, even if an environment value is
empty. Paths are absolute or relative to `android-app/`; `~` is not expanded by
Java properties. Use an absolute path for an external keystore.

| Untracked `android-app/keystore.properties` field | Environment variable |
| --- | --- |
| `storeFile` | `FLINT_UPLOAD_STORE_FILE` |
| `storePassword` | `FLINT_UPLOAD_STORE_PASSWORD` |
| `keyAlias` | `FLINT_UPLOAD_KEY_ALIAS` |
| `keyPassword` | `FLINT_UPLOAD_KEY_PASSWORD` |

If the file and all four variables are absent, the release keeps its existing
debug-key signature for **development-signed preview** builds. Gradle prints that
classification and the release BuildConfig sets `DEVELOPMENT_SIGNED_PREVIEW=true`.
Debug-only account tools remain excluded. Partial/blank credentials or a missing
keystore fail configuration; wrong passwords/alias fail signing. They never fall
back silently. Set `FLINT_REQUIRE_UPLOAD_SIGNING=1` for every intended store build
so a missing configuration also fails. This flag selects signing requirements,
not publication or permission to upload.

The properties file and `.jks`/`.keystore`/`.p12` files are ignored. Keep keys
outside the repository anyway; ignore rules are not a secret store. Java
properties escaping applies, including doubled backslashes on Windows. Avoid
putting passwords in shell history or command-line Gradle properties. Keep local
Gradle configuration caches private because signing configuration contains
credentials; do not attach them to a report.

## Human key generation and custody

1. Choose an owner-controlled private directory outside the repo and a password
   manager for the keystore and key passwords. Create an upload key with the
   official Android Studio signing wizard, or run the following manually; it
   prompts for passwords rather than putting them in arguments:

   ```sh
   keytool -genkeypair -v -keystore /absolute/private/path/flint-upload.jks \
     -alias flint-upload -keyalg RSA -keysize 2048 -validity 10000
   ```

2. Enter the real owner identity in the certificate prompts. Store the key file,
   alias and credentials in two access-controlled backups, with at least one
   offline copy. Record certificate SHA-256/SHA-1 fingerprints and test restoring
   the backup before relying on it. Never send the private key to a reviewer.
3. Populate the untracked properties or a secret-injected local environment.
   Build with `FLINT_REQUIRE_UPLOAD_SIGNING=1 make android-release` and, once the
   bundle target is available, `FLINT_REQUIRE_UPLOAD_SIGNING=1 make android-bundle`.
   Inspect APK certificate fingerprints with SDK `apksigner verify --print-certs`;
   inspect AAB signing with `jarsigner -verify -verbose -certs`. Match the signer
   to the intended upload certificate, not merely the fact that it is signed.
4. In the owner's Play Console, enroll in Play App Signing and choose whether
   Google generates the app-signing key or an existing production key is used,
   according to the actual app history. Register the upload certificate and
   record both upload and Play app-signing fingerprints. Do not invent prior
   enrollment or transfer an unrelated debug key into the production identity.
5. Document authorized custodians, recovery and upload-key reset procedures.
   Keep the private upload key separate from public certificate exports. An
   upload-key reset does not change Google's app-signing key.

## Preview and update compatibility

Public CI/release workflow previews have no owner credentials by default and
must remain labeled development-signed previews. A debug-signed preview cannot
in-place update an installation signed by another certificate. Do not tell users
to uninstall to “fix” that without explaining that uninstall can erase local
rules/history. Prove upgrade/data preservation on the intended Play test track
after owner enrollment; a locally upload-signed APK and a Play-delivered APK can
have different certificates because Play signs delivery with its app-signing key.

Version metadata remains literal `versionName`/`versionCode` in app Gradle.
Before a new tag, update Android versionName to the tag without `v`, strictly
increase versionCode, update iOS marketing version and CHANGELOG, then run
`make release-check TAG=vX.Y.Z`. APK and AAB come from that same configuration;
there is no second bundle version counter. No tag/version bump or release is
created as part of signing setup.
